# Seña — Setup y aislamiento de entorno — kubefin

> Fecha: 2026-09-09

Guía del entorno de desarrollo de kubefin: cómo se aísla la identidad personal de la de trabajo,
qué credenciales usa cada superficie y cómo autenticarse. Complementa a [`RESENA.md`](RESENA.md).

## Por qué este aislamiento

kubefin vive en `scripts-hub/Scripts-Devops/` — **fuera** de `personal-projects/`, así que NO hereda
ningún `.envrc` padre. Sin aislamiento explícito, cualquier `git`, `gh` o `aws` ejecutado aquí usaría
por defecto la identidad de **trabajo** (`jhenao-nex`, cuenta Nexus). Este repo fuerza la identidad
**personal** (`jaimehenao8126`, que administra la org `arheanja-ops`) mediante `direnv`.

## Componentes del entorno

| Archivo | Se commitea | Rol |
|---|---|---|
| `.envrc` | Sí (sin secretos) | Exporta identidad git personal, `GH_CONFIG_DIR` aislado y `AWS_PROFILE`. Carga `.env.local`. |
| `.env.local` | No (gitignorado) | Secretos reales: `GROQ_API_KEY`. Nunca se versiona. |
| `.env.local.example` | Sí | Plantilla de `.env.local`. |
| `.gh/` | No (gitignorado) | Config aislada de `gh` CLI, local al repo. |

### Qué exporta `.envrc`

- **Identidad git personal:** `GIT_AUTHOR_*` / `GIT_COMMITTER_*` = `jaimehenao8126@outlook.com`.
  Ningún commit sale con la identidad de trabajo, sin depender de `includeIf` en `~/.gitconfig`.
- **`GH_CONFIG_DIR=${PWD}/.gh`:** `gh` en este repo usa una config local aislada; nunca toca
  la cuenta de trabajo `jhenao-nex`.
- **`AWS_PROFILE=taxops-admin`:** perfil personal (SSO) para el análisis de costos (Fase 2, read-only).
  Limpia credenciales estáticas heredadas del shell padre.

## Primeros pasos

```bash
cd /Users/jaime.henao/arheanja/scripts-hub/Scripts-Devops/kubefin

# 1. Activar direnv (una vez, y tras cada edición del .envrc)
direnv allow .

# 2. Crear tu .env.local a partir de la plantilla y llenar GROQ_API_KEY (para Fase 3)
cp .env.local.example .env.local
# edita .env.local y pon tu GROQ_API_KEY (console.groq.com, gratis)

# 3. Autenticar gh en el dir aislado (cuenta personal jaimehenao8126)
./scripts/gh-login.sh

# 4. Iniciar sesión AWS SSO personal (para Fase 2 en adelante)
./scripts/aws-login.sh
```

## Scripts de login

- **`scripts/gh-login.sh`** — verifica la sesión `gh` dentro del `GH_CONFIG_DIR` aislado y la inicia
  si falta. Falla explícitamente si `GH_CONFIG_DIR` no está seteado (evita usar la cuenta de trabajo
  por accidente). Usa HTTPS y la cuenta personal.
- **`scripts/aws-login.sh`** — verifica la sesión SSO del perfil personal (`AWS_PROFILE`, por defecto
  `taxops-admin`) y la renueva vía `aws sso login` si expiró.

Ambos replican el patrón ya probado en TaxOps-11.

## Kubernetes: desarrollo local con minikube

Fase 1 (Core EKS con `client-go`) se desarrolla y prueba contra **minikube**, sin tocar clústeres
EKS de trabajo ni requerir AWS:

```bash
minikube start
kubectl config current-context   # debe decir "minikube"
```

kubefin lee el **contexto actual de kubectl** vía `client-go`, así que apuntará a minikube
automáticamente. Para diagnosticar un EKS real más adelante, basta cambiar de contexto
(`kubectl config use-context <eks>`).

## Credenciales por fase

| Fase | Requiere | Fuente |
|---|---|---|
| 1 — Core EKS | contexto kubectl (minikube) | kubeconfig local |
| 2 — FinOps | sesión AWS SSO personal | `AWS_PROFILE=taxops-admin` + `aws-login.sh` |
| 3 — Agente IA | `GROQ_API_KEY` | `.env.local` |

## Regla de oro

- Los secretos SOLO viven en `.env.local` (gitignorado). Nunca en `.envrc` ni en el código.
- Antes de cualquier `git push`, confirma la identidad: `git config user.email` debe ser
  `jaimehenao8126@outlook.com`, no la de trabajo.
